# 竞赛 / 投标交付方法论

> 来源：从一份顶级 RFQ 报价赛道成果报告（团队「电小余」）提炼，经 project-flow-cy 视角泛化。它把"先把问题想清楚再动手"和"不许伪造成功"落成可操作写法。
> 适用：竞赛成果报告 / 投标方案 / 客户交付 PPT / 任何"需要说服第三方、且验证尚未发生"的文档。

---

## 核心：陈述边界（可陈述 / 待验证）

任何对外陈述前，先分两类，且**明文分开列**：

- **可据现有材料陈述**：已落地、已测量、已有证据支撑（含 plan 中已跑通的部分）。
- **需新证据才能陈述**：还在计划里、只跑过 demo、作者自测、未做对比实验。

不允许把"待验证"混进"已验证"的句子里。这一条是整份方法论的承重墙。

---

## 五条可复用实践

### 1. 模型理解 + 规则计算分离
LLM/VLM 只做"识别、抽取、归一、语义"这类不确定但有容错空间的事；价格、税额、单位换算、时点判断、尺寸校验等确定性强的事，交给确定性规则 / 脚本。模型输出只作"建议"，规则作"裁定"。
**跨赛道都成立**：RFQ 价格、图纸尺寸抽取、比价匹配判定——同一原则反复验证有效。

### 2. 陈述边界表（见上「核心」）
写稿前先把"能说 / 不能说"列成表，对外稿只引用"能说"半区。

### 3. 数字带分母和来源
每个比率 / 收益都给"分子 / 分母 / 假设"。写"抵平 123 份询价（月费 980 ÷ 单次成本 10）"而非"效率提升 80%"。
无分母的数字 = 不可证伪 = 等于没说。

### 4. 验证纪律（三铁律）
- **不让研究者 / 作者代操作**——避免无意识引导，抵消实施偏差。
- **原方案 / 产品方案交替顺序**——抵消顺序偏差。
- **失败样本不剔除**——剔除失败 = 伪造基线，等于作弊。

### 5. 依据可查 / 条文回链
每条结论能回链到原文具体条号 + 地址（法规、接口文档、数据来源）。评委随手能验，合规底座扎实。

---

## 反面模式（伪造成功的几种典型写法，禁用）

- "效率提升 80% / 准确率 90%"——无分母、无样本、无基线。
- 把 plan 当 proven——验证全写在"90 天计划"里，对外承诺与实现有 6 处缺口却混为一谈。
- 不绑主办方平台——本赛"主题契合 30%"要求真用指定底座，全文只说"模型"会丢分。
- 公开真实企业数据——演示数据须声明为演示，不得包装成真实企业验证、不得掺内部数据。

## 与 project-flow-cy 的关系

- `charter.md` 钉"不做什么" → 陈述边界的**上游**（先把范围钉死，才有边界可言）。
- `flow/claims.md`（模板见 `assets/templates/flow/claims.md`）→ 陈述边界的**落地台账**，每次写对外稿前先填。
- `decisions.md` → 记"为什么不做某功能 / 选哪个底座 / 哪条路被否决"。
- 跨模型评审（机制 C）→ 验证纪律的**自动化版**（换一双不相关的眼睛找茬，错误不相关 = 免费质量倍增）。
